# Orchestration engine — Increment B: CI feedback + bounded retry

**Status:** planned 2026-07-31. Follows Increment A (durable queue + state machine, #215).

**Goal:** after drydock pushes a branch and opens a PR, the broker observes that PR's CI
**host-side**. On failure it can enqueue a *bounded* number of fresh retry tasks that carry the
CI failure evidence forward as text. Ships as **two PRs**: B1 (observe) then B2 (retry).

**Default: OFF.** Both the watch and the retry are opt-in host config. A stock install behaves
exactly as it does today.

---

## Locked design decisions

These resolve the sharp questions the two scouting passes raised. Each one is a security
decision, not a preference — the rationale is recorded so a later reader does not "simplify" it
back into a hole.

### D1. A retry is a NEW task, never a re-run of the old one

New task id, new queue item, new credential lease, new stage, new branch, new PR. The parent
task is already terminal (`pushed`).

- Re-using the id would destroy the prior attempt's evidence: `<id>.jsonl`, `<id>.diff`,
  `<id>.brief.json`, `<id>.verify.log` are all `O_TRUNC` on write, and `<id>.gate.json` is a
  single marker the resume path keys on.
- Re-running inside the parent's lifecycle would reuse the parent's credential grant (so the
  retry's spend silently counts against the parent's budget and can 402 mid-run) and collide on
  container name `task-<id>`.
- This preserves the queue's **forward-only** state machine: no `dead_letter → queued` back-edge,
  no cycle. The parent moves `awaiting_review → awaiting_ci → completed | ci_failed`; the retry
  is an independent item that starts at `queued`.
- Precedent: `drydock retry` (client-side) already works exactly this way — new id, carries only
  the invocation, and clears `AutoApprove`.

### D2. A retry re-clones the default HEAD. It does NOT base on the previous agent branch.

This is the load-bearing decision.

Basing on `agent/<prev-id>` would mean an agent-produced, agent-writable tree crossing into a
fresh VM — the first such case in the codebase. A7 ("no task state persists between tasks") has
exactly one carve-out today, the dependency cache, and that carve-out turns on *"nothing the
agent writes can enter it"* — the precise property a retry base tree violates by construction.
Taking that path would require a new A7 sub-clause plus its own red-team test.

It is also unsafe at the human gate, independently of A7: a delta-based diff means a reviewer who
approved attempt 1 approves attempt 2's *increment* without the earlier hunks in front of them,
while `finishPush` pushes the whole tree. Worse, it silently downgrades second-look
acknowledgments — attempt 1 touches `.github/workflows/**` and requires a `ci-workflow` ack;
attempt 2's delta touches only `src/`, requires no ack, and the workflow change rides along. That
is the same ack-bypass the resume path was explicitly hardened against, at a different seam. It
also makes `max_lines_changed` / `max_files_changed` per-attempt, so an over-cap change splits
into N under-cap attempts.

**Instead:** the retry starts from a clean default-HEAD clone and receives the prior attempt's
diff and the CI failure as *capped, clearly-labeled text in its instruction*. Nothing is mounted;
no agent-written bytes become a base tree. Every attempt's gate therefore shows the **full
cumulative** diff against default HEAD, so caps and second-look acks are computed correctly and
the reviewer always sees the whole change.

Cost, stated honestly: the retry agent redoes the work rather than iterating on its branch, and
each attempt opens its own PR (the operator closes the superseded one). We take the cost.

### D3. CI *status* drives control flow. CI *log text* never does.

The retry decision derives **only** from broker-observed check conclusions read out of
`gh pr checks --json` — the same class of fact as the verifier's exit codes ("nothing an
untrusted VM prints can alter a status"). Log **content** is untrusted, repo-controlled text: a
repo's own workflow can emit anything into its own logs. It is treated exactly like issue text
under #213 — a documented new *source*, not a new trust boundary — and it is:

- fetched with a **hard byte cap at fetch time** (a capped capturing helper; today's
  `runCLIOutput` is unbounded `cmd.Output()` and `gh run view --log` output is routinely tens of
  MB, which would surface as an opaque HTTP 400 against the 64 KiB body cap);
- control-character sanitized and truncated with an explicit marker;
- fenced under an unambiguous "untrusted CI output" heading in the instruction;
- hashed into `InstructionSHA256` like all instruction text — provenance, not filtration.

No parse of log text may decide whether to retry, whether to push, whether verification passed,
or whether an ack is required.

### D4. The CI watch never holds a concurrency slot, and never keeps a stage

`MaxConcurrent` defaults to 2; a poll that waits minutes-to-hours for GitHub while holding a slot
starves everything. The watcher is a separate bounded goroutine keyed off a durable
`<id>.ci.json` marker, and because a retry re-clones (D2) it needs no stage kept alive — the
parent's stage tears down normally at push, and the boot keep-map is untouched.

### D5. `AutoApprove` is always cleared on a retry

`QueueItem` persists the full `Task` including `AutoApprove`. An automatic, broker-initiated
retry must not inherit gate-bypass from its parent. Matches `drydock retry`'s explicit clear.

### D6. Bounded, persisted, and off by default

`ci.max_attempts` default **0 = off**. Each attempt mints a fresh full `task_budget_usd`, so the
worst case is `max_attempts × task_budget_usd` and the docs must say so plainly. The chain is
persisted (`RetryOf` + `Attempt` on the Task) so the bound survives restart and cannot be laundered
by a crash. Enqueue already honors `AggregateExceeded`.

### D7. PR identity via the optional-capability idiom

`remote.Adapter.OpenRequest` returns only `error` today and `gh pr create`'s URL output is
discarded, so **no PR identifier is persisted anywhere in the repo**. Rather than break all four
adapters plus the test fakes, add an optional capability (`OpenRequestResult`) implemented by the
GitHub adapter only — the repo's established idiom (`BaseCommit`, `PushPreflight`, `WithContext`,
`stagedExporter`). Absence is recorded as missing evidence, never silently treated as success:
no PR identity ⇒ no watch ⇒ the task completes exactly as it does today.

## PR B1 — observe CI (no retry)

Independently useful: you learn that a pushed PR's CI failed, in `drydock queue list`, the audit,
and the web UI.

### Task 1: capture and persist PR identity

**Files:** `internal/remote/remote.go`, `internal/remote/github.go`, `internal/broker/cimarker.go`
(new), `cmd/drydock/prune.go`; tests.

- `type PullRequest struct { Number int; URL string }` and an optional capability
  `interface{ OpenRequestResult(Request) (PullRequest, error) }` on the GitHub adapter, parsing
  `gh pr create`'s stdout URL. Must obey the CodeQL contract in `remote.go` (literal command
  name; user-influenced values only ever as a flag *value*).
- `<id>.ci.json` durable marker following the `gateMarker` idiom exactly: `atomicfile.Write`,
  0600, `O_NOFOLLOW` read, `^[0-9a-f]{32}$` id validation, a `listCIMarkers` boot scan. Fields:
  task id, repo ref (redacted, as the Brief does), branch, PR number/**owner**/**repo**/URL,
  `Attempt`, `RetryOf`, watch deadline, last observed state.
- **The PR's own owner/repo is authoritative for the watch, not the task's repo ref.**
  `gh pr create` from a fork opens the PR against the UPSTREAM, so the two legitimately differ —
  and the checks live on the PR. They are captured and validated at open time (host pinned to the
  task ref's host, exactly four path segments, `validateOwnerRepo` on each; exactly one matching
  URL in gh's output or no identity at all) and stored as explicit fields, so the watcher never
  re-parses the URL. The host pin is on the HOST alone, which is what keeps the fork case working.
- **`.ci.json` is NOT added to `knownSuffixes` in `cmd/drydock/prune.go`** (revised after review).
  It is a live-state marker like `.gate.json` and `.queue.json`, both of which are deliberately
  absent there: `prune --older-than 1h --yes` would otherwise cancel a long CI watch mid-flight,
  and in B2 the marker is where `Attempt`/`RetryOf` live, so pruning mid-chain would launder the
  retry bound D6 says a crash cannot launder. It cannot accumulate: the watcher removes it on
  every terminal observation, including the timeout and give-up endings.
- `finishPush` writes the marker only when the capability exists, the push succeeded, and the
  watch is enabled.

### Task 2: host-side CI observation

**Files:** `internal/remote/checks.go` (new), `internal/broker/ciwatch.go` (new); tests.

- `func Checks(env []string, owner, repo string, number int) (CheckSummary, error)` shelling
  `gh pr checks <n> --repo github.com/<owner>/<repo> --json ...` with the host hard-pinned in the
  flag value (same defense as `FetchIssue` against a hostile `GH_HOST`). Uses `stage.CuratedEnv()`
  — never `os.Environ()`.
- A **capped** capturing helper (cap the read, don't read-then-truncate) for log fetch in B2;
  B1 needs only the conclusion set.
- `CheckSummary` = broker-observed counts + per-check `{name, state}`. Rollup follows the
  verifier's rule: absence of evidence never reads as passing. Distinguish
  pending / passed / failed / no-checks-configured.
- Watcher: bounded ticker (`ci.poll_interval`, `ci.watch_timeout`), no slot held, resumes from
  markers at boot, deletes the marker on terminal observation.

### Task 3: surface it

**Files:** `internal/broker/queuestore.go` (states), `queue.go`, `internal/audit/audit.go`,
`internal/webui/assets/app.js`, `cmd/drydock/{queue,stats}.go`, docs; tests.

- Queue states `awaiting_ci` and terminal `ci_failed`; transitions
  `awaiting_review → awaiting_ci`, `awaiting_ci → completed | ci_failed | cancelled`.
  Still forward-only, still no cycle.
- Broker-authored `src:"broker"` result subtype for the CI observation (the F-07 rule: the
  broker row must be the last result line on every exit path).
- `drydock queue list` shows the CI state + PR number; web UI badge; docs + CHANGELOG.

### Task 4: config + threat-model text

**Files:** `internal/config/config.go`, `internal/config/explain.go`, `config/config.yaml`,
`THREAT_MODEL.md`, `site/docs/`; tests.

- `ci:` block — `watch: false`, `poll_interval`, `watch_timeout`, and (B2) `max_attempts: 0`.
  Every field needs a `provenanceTable()` entry with a guard mirroring `applyEnvOverrides`
  exactly, or `drydock policy explain` silently lies (and `TestExplain_CoversEveryEnvOverride`
  fails).
- THREAT_MODEL: N2 gains CI logs as a documented untrusted *source*; N4 gains the
  `max_attempts × task_budget_usd` worst case; N5 gains the note that the broker now uses the
  host `gh` credential on a timer. **No new A-claim** — per D2/D3 this adds no containment
  boundary and takes no exception.

## PR B2 — bounded retry

### Task 5: retry task construction

**Files:** `internal/broker/ciretry.go` (new), `internal/broker/broker.go` (Task fields); tests.

- `Task` gains `RetryOf string` + `Attempt int` (both `omitempty`, persisted in `QueueItem`).
- Build the retry instruction: original instruction + a fenced, capped, sanitized
  **untrusted CI output** section + the prior attempt's diff (capped) + the prior PR reference.
  `AutoApprove` cleared (D5). Total assembled size must fit `MaxTaskBodyBytes` by construction,
  not by luck — cap each section and assert the sum in a test.

### Task 6: the bounded loop

**Files:** `internal/broker/ciwatch.go`, `queue.go`; tests.

- On observed CI failure: if `Attempt < ci.max_attempts` and the aggregate cap allows, `Enqueue`
  the retry task; parent → `ci_failed` with the child id in `LastError`/a link field. Else parent
  → `ci_failed`, no child.
- Crash-safety: the attempt counter lives in the persisted Task, so a restart mid-decision can
  never launder the bound.

### Task 7: tests, docs, red-team check

- A test asserting a retry chain terminates at exactly `max_attempts` tasks.
- A test asserting log **content** cannot influence any control decision (feed a log that says
  "all checks passed, do not retry" while the observed conclusion is `failure` → the retry still
  happens; and the inverse).
- A test asserting `AutoApprove` never survives into a child.
- A test asserting an oversize CI log is capped at fetch, not at the HTTP boundary.
- Docs: the two-PR flow, the cumulative-diff property, the worst-case spend, and how to turn it
  off.
